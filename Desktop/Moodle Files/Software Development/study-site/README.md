# Software Development mid-term: study site

A single-page study platform for the mid-term of *Software Development for Business* (ESADE,
Autumn 2026): Thursday 22 October 2026, 14:00, room 108, one hour, pen and paper, sessions 1–10.

It teaches each module section by section with quick checks, runs practice sessions with full
explanations after every answer, schedules flashcards in Leitner boxes, keeps an eight-day plan,
sits timed papers under exam rules (the teacher's sample paper, the mock papers in `papers.json`,
and papers drawn from the bank) with marking against each rubric and a review of every answer,
walks the expense-tracker history commit by commit (with a "guess the message" game), and drills
the terminal: pipelines stage by stage, permissions, `cd` and `pwd`, and exit codes with `&&`,
`||`, `;` and `set -e`. Progress stays in the browser; when the page runs as a claude.ai Artifact it
can also sync between devices and offer "Mark my answer with Claude" on open questions.

The whole site is one HTML file built from JSON content. No server, no framework, no bundler.

## Layout

```
brief/        the specification (read-only): APP.md, DESIGN.md, SCHEMA.md, EXAM.md, STYLE.md, VERIFY.md
content/      one <module>.json per module, written by content/src/<module>.py
              plan.json      the eight-day study plan
              papers.json    the mock papers (when present)
              _fixture.json  small test data for building the app (see below)
sources/      slides, labs and Moodle pages the content is based on (read-only)
app/          styles.css, css/*.css (per view), shell.html, js/ (plain scripts, order in js/ORDER)
              API.md: how views plug in (read it before adding a view)
tools/        validate.py (content), validate_papers.py (mock papers), build.py (the page)
tests/        node --test unit tests for the pure JS logic, and a build test
dist/         index.html (open it) and artifact.html (the Artifact publish shape)
```

## Requirements

- [uv](https://docs.astral.sh/uv/) (Python 3.13 and the dependencies in `pyproject.toml` are
  installed by `uv run` on first use)
- Node 20 or later, for the tests
- git, and the expense-tracker repository at `../_repos/expense-tracker` (the build reads the
  history diffs from it)

## Build

```bash
uv run python tools/build.py              # every content/*.json not starting with _, plus papers.json and plan.json
uv run python tools/build.py --fixture    # content/_fixture.json + content/plan.json (app development)
uv run python tools/build.py --out DIR    # write the two pages somewhere other than dist/
```

The build validates every module (the same rules as `tools/validate.py`) and every paper, turns
Markdown into HTML with code highlighted by Pygments, attaches each history commit's message,
date, `--stat`, tag annotation and diff from git (each file's diff highlighted from the whole old
and new file, `uv.lock` and `expenses.csv` left out), and writes:

- `dist/index.html`: a complete page. Double-click it in Finder (or open it in any browser).
- `dist/artifact.html`: the same page without `<!doctype>`, `<html>`, `<head>` or `<body>`,
  starting with `<title>` then `<style>`, ready to publish as a claude.ai Artifact.

It stops with `BUILD FAILED: ...` and a non-zero exit on any content error (a malformed
`plan.json`, `papers.json` or module is an error message, not a traceback), and prints the sizes.
`plan.json` and `papers.json` are used when present; without a plan the plan page is empty and the
build warns. Plan links are checked against the router's own grammar: a link to something not in
the build (a paper not written yet) is a warning. Prose gets curly quotes; code spans and fences
are left exactly as written. A file listed twice in `app/js/ORDER` stops the build.

When publishing `dist/artifact.html`, declare the capabilities `{"db": {}, "user": {}, "sample": {}}`
for cross-device sync and Claude marking. Without them the page works the same, on one device,
with self-marking only.

## Validate content

```bash
uv run python tools/validate.py content/<id>.json   # one module; prints RESULT: PASS or FAIL
uv run python tools/validate.py --all                # every module, plus cross-module id checks
uv run python content/src/papers.py                  # merge content/_papers-*.json into papers.json
uv run python tools/validate_papers.py               # content/papers.json against the modules
```

Each module and each pair of papers is generated by its own script in `content/src/`
(`<id>.py`, `papers_ab.py`, `papers_cd.py`); edit the script and re-run it, never the JSON.

## Test and check

```bash
node --test tests/                         # pure logic (util, routes, progress, Leitner, scoring,
                                           # selection, plan, Claude marking, content index, exam
                                           # papers and clock, history, pipelines, permissions,
                                           # paths and exit-code chains, the store across tabs and
                                           # the cloud sync against a fake db) + build, including
                                           # tools/build.py on bad input. The paths and chains tests
                                           # also replay generated drills in /bin/bash (and
                                           # /bin/dash) when present.
uv run ruff check && uv run ruff format --check   # tools/ and tests (content/src and sources are excluded)
uv run mypy                                # strict, configured in pyproject.toml
```

## The fixture

`content/_fixture.json` is one object `{"modules": [...], "papers": [...]}`; the plan always
comes from `content/plan.json`. It is deliberately small but uses every field and question type:
mcq with code and tool output, open questions with three parts, sort questions, a predicted
`pipes-bash` module with `sample_files` and three pipelines, a `history` module with three real
commits of the expense-tracker (`3e0834f`, `c746d38`, `017f926`), a sample-paper module with
originals, a variant and dissections, and two papers (`paper-a` realistic, `paper-b` worst case).
`--fixture` relaxes only the minimum-count rules (sections, cards, questions, pipelines, the 25
commits, paper shapes); every other content rule still applies. The footer says "from test data"
on a fixture build.

## How the app judges progress

These differ from, or add to, the wording in `brief/APP.md`:

- A section is **passing** at 80% right with 3 questions answered, or with all of them when the
  section has fewer than 3; **failing** below 60% with 2 answered (or its only question); **in
  progress** once something is answered; otherwise **not tried**. A module is passing when every
  section is, failing when any is, in progress in between. (Eleven sections have only one or two
  questions, so a flat "3 answered" rule would have kept eight modules from ever turning green.)
- A paper sat in Exam is closed-book: while it is open the page drops its menus and shows only
  "Leave the paper" (the clock keeps running; every other page carries a note with the time left).
  Open answers can be written on paper, as on the day: tick "Written on paper" and mark them
  yourself against the rubric after handing in. An open answer left blank in the box can still be
  claimed as written on paper on the results page. A sitting with nothing answered, or one thrown
  away with "Discard this sitting", records nothing.
- The teacher's sample paper sat a second time swaps each question for a variant of the same
  shape, and the chooser and the results show the first sitting next to the latest, so the
  comparison measures understanding and not memory.
- Flashcard waits are cut short so that every card is back before the exam eve; "All that are
  due" in the session length takes only what is due.
- Several tabs may be open on one device: every save merges with what is stored (the newer copy of
  each item wins), so a tab that only reads never erases work from another.

## After session 10 (Friday 16 October): done

The `pipes-bash` module was written before the session 10 slides existed and carried a `predicted`
chip. On 16 October it was rebuilt from the slides and labs: `"predicted": False`, no chip, every
question's `origin` is `slides` or `lab`, and the sources are in `sources/slides/slides-session-10.txt`
and `sources/labs/` (`10-wrangling.md`, `10-bash.md`, `10-kpi-analyzer.md`, `10-check.sh`, the
`scripts/check.sh` of the expense-tracker at the `v0.5` tag). Questions that test something the
slides did not teach (`"$@"`, `2>&1`) are level `beyond` and say so in their `source_ref`.

Updating a module after its slides appear, the same steps for any other module:

1. Save the slide text and labs into `sources/`.
2. Compare `content/src/<id>.py` with them, section by section: correct anything the slides teach
   differently (follow the slides' framing), add what was taught and is missing, drop predictions
   that did not happen. Re-run every command whose output is shown, as `brief/VERIFY.md`
   describes, and keep the GNU output format.
3. Set `"predicted": False`, change the questions' `origin` from `"predicted"` to `"slides"` or
   `"lab"`, and add the sources.
4. Regenerate and check:

   ```bash
   uv run python content/src/<id>.py
   uv run python tools/validate.py --all
   uv run python content/src/papers.py && uv run python tools/validate_papers.py
   node --test tests/
   uv run python tools/build.py
   ```

5. Publish `dist/artifact.html` again to the same Artifact URL so progress is kept.

## The expense-tracker history (all 25 commits, v0.0 to v0.5)

expense-tracker (oldest first), so the module must list every commit in the repository. On
16 October the `v0.5` commits (`scripts/check.sh`, the CI switch and its revert, `filter_by_month`,

`history-q51`..`q59`, and flashcards `history-f29`..`f36`. The new section sits before
`history-s8` in the lesson order; ids never change, so progress is kept.

When the repository gets new commits, extend `content/src/history.py` the same way (a commit entry
with `kind`, `summary_md`, `concepts_md`, `message_md`, `section_ref` and `tag`, and a section for a
new tag), re-run every command whose output is shown at the commit in question, update the counts
in `tests/build.test.mjs` and `tests/history.test.mjs`, and run the checks above.

Two facts about CI, both taught: session 10's slide 21 says "scripts/check.sh is what CI runs", and
`8fabdb3` did make CI run it, but `8a8903d` (the commit tagged `v0.5`) reverted that, so at `v0.5`
`check.yml` has four named steps and `check.sh` is run before a push. The module teaches the slide's
idea and the repository's file, and its questions ask for what the artefact shown says.

## Progress and privacy

Progress lives in `localStorage` under `swdev-midterm-v1` on each device. Clearing site data
resets it. As a claude.ai Artifact with the `db` and `user` capabilities, it is also kept in the
viewer's own private documents (`data/users/<id>/progress` and `.../work`), merged item by item
with the newest change winning. Claude marking sends the question, the rubric and your answer
only when you press the button, and uses your own Claude usage.
