===== [slides-session-3.pdf] page 3 =====
Why we standardise — and what is actually required
"Works on my machine" is the single problem this whole course is built to solve. We aim
to systematize how dependencies and builds happen, so that the artifacts produced by the
code are reproducible.
You may use any operating system and any editor. That is your freedom.
Two things are not negotiable:
1. Your work passes the CI check — the automated ruff + mypy + pytest run on
GitHub. That is the referee.
2. The recommended path is the only one supported by the lecturer. Off-path is allowed,
but at the expense of your own time.

Six tools
Tool
One sentence
WSL2
A real Linux kernel inside Windows. The course lives in a Linux shell. (macOS/Linux: you already
have one.)
VS
Code
The editor. On Windows it runs outside WSL and reaches in via the Remote-WSL extension.
uv
Installs Python itself and your project's dependencies == the same versions for everyone.
git
Records the history of your code. Today we do bare minimal setup.
GitHub
Where your group's repository lives. You authenticate to it with an SSH key.
Docker
Runs your project in a container. Not needed until session 16. Install it today if it is painless, skip
it if it fights.

===== [slides-session-3.pdf] page 6 =====
What a virtual environment actually is
In three minutes.
Python looks up packages in a fixed list of directories.
A virtual environment is just another such directory, one per project, that Python is
told to look in first.
So "install a package" means "put it in this project's directory", not "change the
whole computer".
uv makes and fills that directory from your pyproject.toml . uv run uses it.
That is the entire idea. No magic.

===== [slides-session-3.pdf] page 10 =====
Clone the group project repo, take your own branch
Your group repository already exists. Four of you push to it in the same twenty
minutes — on main , only the first would succeed. So you each take a branch.
cd ~
git clone git@github.com:esade-swdev-2026/<your-group>.git
cd <your-group>
git switch -c setup/<your-github-username>
switch -c = "make a new branch and move onto it". Yours alone; nobody can collide
with you on it.

===== [slides-session-3.pdf] page 14 =====
Push the report — watch CI go green
The moment the whole session is built toward.
1. You pushed your report to your own branch of your group repo.
2. Open the repo on GitHub → Actions tab.
3. A workflow called check is running, on your branch. Watch it.
4. Green = the referee accepts your repo. This check now runs on every push you make
all term. From module 4, when you merge through pull requests, a red check blocks the
merge.
Red on the report but green on Actions is fine — the report is your to-do list; Actions
checks the repository.
