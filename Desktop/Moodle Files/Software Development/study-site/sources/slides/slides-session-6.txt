    t = 0

        t += p[1] * p[2]
    if d > 0:
        t = t - (t * d)
    if i > 0:
        t = t + (t * i)
    return t

===== [slides-session-6.pdf] page 11 =====
A disagreement, out loud
It is standard practice in introductory courses to comment liberally.
The reason is that in a learning context it is good to explain what the code does.
However, we will apply the following rule:
A comment that explains what the code does is a failure of naming.
The reason, as explained by Robert C. Martin:
"Truth can only be found in one place: the code."
The advice makes sense depending on context; never follow it blindly.

Magic numbers
This is how we call constants that appear in the code without a name. In general it is better to
name them as constants.
print("-" * 40)
print(name.ljust(20) + amount.rjust(10))
RULE_WIDTH = 40
NAME_WIDTH = 20
AMOUNT_WIDTH = 10
Change the width once, in one place, with a name that says what it is. if e[3] < z
becomes if expense[AMOUNT] < minimum .

Computation is not output
def total_by_category(expenses, category, minimum):   # returns data
    ...

    ...

A function that returns can be tested, reused and read on its own.
A function that prints can only be looked at.

===== [slides-session-6.pdf] page 24 =====
dataclass is a naming tool
Not a Python feature to memorise. It is how you give a name to business domain concepts.
frozen=True : it does not change after creation
The editor autocompletes expense.
A typo in a field name is an error, not a silent wrong answer
Every group project has concepts that can be modelled with a dataclass: a booking, a
product, a match, a reading...
